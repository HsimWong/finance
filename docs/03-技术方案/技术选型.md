# 技术选型与架构

> 依据原始构想第 11 条：后端无框架 Go（可用库）、前端无框架纯 HTML+CSS+JS、本地 SQLite、图片入库。

## 决策一览

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 后端 | Go 1.26 标准库 `net/http`，不引 Web 框架 | 符合「无框架 Go」；标准库足以支撑 REST + 静态托管 |
| 数据库驱动 | `modernc.org/sqlite`（纯 Go，无 CGO） | 本机无 gcc，`mattn/go-sqlite3` 需要 CGO 会编译失败；纯 Go 驱动无需 C 工具链，Windows 上可直接 `go run` |
| 数据库 | SQLite 单文件 `data/finance.db` | 本地、零运维、单文件可备份 |
| 前端 | 原生 HTML + CSS + ES Modules，零构建 | 符合「不使用框架」；由 Go 直接静态托管，无 npm、无打包 |
| 金额 | `INTEGER` 存「分」 | 避免浮点误差，聚合求和精确 |
| 图片 | 原始字节存 `screenshots.data` BLOB | 按用户要求「图片也入库」，见下方专章 |
| 部署 | 本机 `localhost`，单机单进程 | 家庭成员 2 人、局域网使用；一期不做登录与公网暴露 |

## 关于「图片存 SQLite 是否适用」

**结论：适用，家庭量级下完全没问题，可以按你的想法入库。**

- 量级估算：一天 10 张截图 × 300 KB ≈ 3 MB/天，一年约 1 GB。SQLite 单库在数 GB 级别仍可正常工作（其上限是 TB 级），瓶颈不在容量而在备份与写入放大。
- 好处：截图与流水在同一个库里，备份 / 拷贝 / 恢复只需一个文件，不会出现「数据库里有记录、图片文件丢了」的不一致，事务上也能保证一致写入。这对家庭自用的单机系统是最省心的方案。
- 注意事项（已在实现中处理）：
  1. BLOB 单独放 `screenshots` 表，流水表只存外键，查询流水列表时不会把图片读进内存；
  2. 原图通过独立接口按需加载（懒加载），前端列表只显示缩略占位；
  3. 上传做大小与 MIME 校验，默认上限 10 MiB；
  4. 定期 `VACUUM` / 备份时留意库体积增长。
- 如果将来图片量变大感觉吃力，可以平滑切到「图片写磁盘、DB 只存路径」：接口路径 `/api/screenshots/{id}/image` 不变，只改存储实现，前端与流水数据无需改动。因此现在入库不是不可逆的决定。

## 目录与运行

```
src/backend/        Go 服务（go.mod、main.go、内部包）
src/frontend/       index.html、css、js（原生）
data/finance.db     SQLite 数据文件（运行后生成，不入库版本库）
```

```bash
cd src/backend
go run .
# 浏览器打开 http://localhost:8080
```

## 接口风格

- 全部 `application/json`，`POST` 支持 JSON；截图上传用 `multipart/form-data`。
- 统一响应：`{ "ok": true, "data": ... }` 或 `{ "ok": false, "error": "..." }`。
- 路径参数用 Go 1.22+ 的 `ServeMux` 方法匹配模式（`/api/entries/{id}`），无需第三方路由库。
- 一期不做鉴权（默认本机 / 局域网可信环境）；接入公网前必须补上。

## 本地 OCR（增量 2 新增）

本机没有 Tesseract，也没有可用的系统 OCR 调用权限，而中文 OCR 没有成熟的纯 Go 实现。方案是**保持 Go 后端无框架**，把 OCR 做成可插拔的外部适配器：

- `scripts/ocr.py` 使用 **RapidOCR + ONNX Runtime**，自带中英文模型，纯本地离线推理，无联网、无密钥。
- Go 通过 `exec.CommandContext` 把**图片原始字节从 stdin 喂给脚本**，脚本从 stdout 回一行 JSON（文本行、坐标、置信度）。不落临时文件。
- `OCRProvider` 接口只约定「图片字节 → 文本行」，将来换 Tesseract / 云 OCR / 多模态模型只需替换适配器。
- 启动时同步自检，未安装依赖时给出明确提示，并保留「粘贴文本解析」兜底，同一套解析规则继续可用。
- 安装：`python -m pip install rapidocr_onnxruntime`；可用 `-ocr-python` 指定解释器。
- 详细规则见 `docs/02-功能设计/OCR与库存联动.md`。

## 依赖清单

- Go 标准库：`net/http`、`database/sql`、`encoding/json`、`mime/multipart`、`os/exec`、`regexp`、`time`、`path/filepath` 等。
- Go 第三方：**仅** `modernc.org/sqlite`（及其间接依赖），用于 SQLite 驱动。无 Web 框架、无 ORM、无路由库。
- 外部工具：Python 3 + `rapidocr_onnxruntime`（仅用于本地图像识别，不是 Go 运行时依赖，可整体替换）。
- 前端：零依赖、零构建。
