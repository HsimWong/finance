# ADR 0002 · 试用期间的数据库保护策略

- 日期：2026-11-13
- 状态：已生效，已实测
- 触发：用户清空演示数据开始试用，并明确要求「期间如果有任何新的需求，需要动数据库，一定要保存好真实的数据」。

## 背景

1. 试用开始后库里会写入**真实家庭财务数据**（流水、截图 BLOB、库存、预算），不可再生。
2. 本项目按敏捷增量推进，后续新需求很可能要加字段、加表、改枚举或做数据迁移 —— 每一次都是潜在的数据事故。
3. **WAL 陷阱**：连接串启用了 `journal_mode(WAL)`，实测清空前主文件 `finance.db` 仅 4 096 B，而 `finance.db-wal` 有 700 432 B，绝大部分数据还在 WAL 里。此时「复制 finance.db 文件」得到的几乎是空库，是本项目最危险的错误备份方式。
4. 现有 `openDB` 只做 `CREATE TABLE IF NOT EXISTS`，没有结构版本概念；将来用 `ALTER TABLE` 时无法保证变更前有可回档的快照。

## 决策

### D1 · 备份只走 SQLite 在线备份 API

- Python 工具用 `Connection.backup()`，Go 服务用 `VACUUM INTO`（二者都输出**包含 WAL 已提交数据**的单文件一致性快照）。
- 明确禁止把 `finance.db` 当备份复制；回档后还要删除旧 `finance.db-wal` / `-shm`，否则旧日志会覆盖恢复结果。
- 每份备份附同名 `.json` 元数据：时间、标签、大小、SHA-256 前 16 位、`PRAGMA integrity_check`、`user_version`、各表行数，可用 `verify` 复核是否被改动。

### D2 · 结构版本化 + 变更前强制备份

- `src/backend/backup.go` 维护 `schemaVersion`（当前 v1）与 `migrations[版本号]`。
- `openDB` 顺序改为：**已有库 → `preSchemaGuard`（版本落后时先备份）→ 启动快照 → 幂等 DDL → seed → `applyMigrations` 写新版本号**。
- 变更前备份失败 → **直接中止启动**，不执行任何 DDL，宁可服务起不来也不拿真实数据冒险。
- 今后加字段的标准动作：`schemaVersion+1`、在 `migrations` 登记语句、其余交给守卫。

### D3 · 启动快照兜底

- 每次启动生成一份 `*_startup.db`（30 分钟内重启不重复），滚动保留最近 20 份，自动清理只针对 `startup` 标签。
- `before-migration-*` / `before-reset` / `before-restore` / 手动标签的备份**永不自动删除**。
- 作用：即使某次改动忘了手动备份，也总能回到最近一次启动时的完整状态。

### D3b · 运行时定时快照（18:30 补充）

- 起因：用户强调「试用阶段写入的是真实数据，需要严格保护」。原 D3 只在启动时快照，服务连续开几天时，当天早些时候的误删无法找回。
- 实现：`startSnapshotLoop` 每 `-snapshot-interval`（默认 30m，可设 `0` 关闭）计算一次数据指纹（流水数/金额合计/最后更新时间、截图张数与字节数、库存数量、预算金额、基础配置数量），**只有变化才备份**，避免产生大量重复文件。
- 每天第一份标 `daily-YYYYMMDD` **永久保留**；其余标 `auto`，滚动保留 48 份（约覆盖 24 小时）。
- 回归测试：`src/backend/backup_test.go` 以 150 ms 间隔验证「无变化不备份」「数据变化后生成快照且快照内含新数据」。
- 粒度取舍：30 分钟内的误删，最多回到上一轮快照；数据量小的时候可把间隔调小（如 `-snapshot-interval 5m`），代价是备份更频繁。

### D4 · 单一工具入口 `scripts/db_admin.py`

| 命令 | 行为 |
| --- | --- |
| `info` | 各表行数、WAL 附属文件大小、完整性、结构版本 |
| `list` | 列出全部备份及行数摘要 |
| `backup --label X` | 手动备份（永久保留） |
| `verify <file>` | 完整性 + 哈希 + 元数据行数一致性 |
| `reset --yes` | **先自动备份**，再清空业务表 |
| `restore <file> --yes` | **先备份现状** + 校验目标备份完整性，再回档 |

- `reset` / `restore` 会检测 8081 端口，**服务仍在运行时拒绝执行**（避免 WAL 中的在线写入覆盖结果），可用 `--allow-running` 强行绕过但不建议。
- `reset` 只清 6 张业务表（entries、entry_tags、allocations、screenshots、stock_items、stock_movements），保留 `members` / `categories` / `tags` 基础配置，并重置自增 id、`VACUUM` 收缩文件。

### D5 · 变更纪律

> 备份 → 验证可恢复 → 才动代码 / 结构 → 启动后核对行数。

具体：`python scripts/db_admin.py backup --label before-需求名` → `verify` → 改代码 → 重启 → `info` 核对。回档演练证明该链路可用（见下）。

## 后果与未覆盖的风险

- **同盘风险**：备份与数据库在同一块磁盘，只能防误操作与迁移事故，不能防磁盘损坏。需定期把 `data/backups/` 复制到外部介质或网盘（已写入 README）。
- **快照粒度**：运行时快照默认 30 分钟一轮，30 分钟内的误删最多回到上一轮；需要更细可调小 `-snapshot-interval`，代价是备份更频繁。
- 未做备份加密与异地同步；库内含家庭财务截图，外部介质需自行保管。
- 启动快照会随截图 BLOB 增长而变大（保留 20 份），后续数据量大了可调整 `maxStartupBackups`。
- 结构迁移目前只做「加版本 + 备份」，尚无破坏性 DDL；真正做 `ALTER TABLE` / 数据回填时，仍需在 `migrations` 中写语句并先跑一次回档演练。
