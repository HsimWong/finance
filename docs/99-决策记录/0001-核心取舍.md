# ADR 0001 · 一期核心取舍

日期：2026-11-13　状态：已采用（可随需求调整）

## 1. 截图图片入 SQLite BLOB

- **背景**：用户要求「截图保存在服务端」，并询问「图片也入库，不知道是否适用本地 sqlite」。
- **决定**：图片原始字节存 `screenshots.data` BLOB，流水表只存外键。
- **理由**：家庭量级（约 1 GB/年）SQLite 完全可承受；单文件备份、事务一致、无「记录与文件不一致」问题。
- **可逆性**：高。读取统一走 `/api/screenshots/{id}/image`，将来改成磁盘存储只需替换实现，前端零改动。
- **代价**：库文件体积随图片增长；定期备份 / VACUUM 需要留意。

## 2. 分类树 + 标签双维度，而非单层分类

- **背景**：三个目标查询性质不同——「A 人员外卖」（成员×细分品类）、「全家交通」（领域汇总）、「猫咪」（跨领域对象）。
- **决定**：`categories` 做可嵌套的领域树作为主归类；`tags` 做多对多横向切片；查询可任意组合。
- **理由**：若把「猫咪」塞进分类树，会与「餐饮/医疗」等维度打架，导致重复分类或无法交叉统计。双维度让「猫咪在医疗上花了多少」这类问题也能回答。
- **代价**：录入时可能要选分类 + 标签两个字段；前端用快捷标签按钮缓解。

## 3. 纯 Go SQLite 驱动（modernc.org/sqlite）

- **背景**：本机无 gcc，`mattn/go-sqlite3` 依赖 CGO 无法编译。
- **决定**：使用 `modernc.org/sqlite`，保持「无框架 Go + 允许用库」的约束，且 `go run` 无需 C 工具链。
- **代价**：包体积较大、首次编译稍慢；对本机自用无实质影响。

## 4. 一期不做登录与自动识别

- **决定**：一期只做「手动上传截图 + 人工确认字段」的可运行闭环，`screenshots.status` 与 `entries.source` 预留二期扩展位。
- **理由**：敏捷增量，先把已确定的记账主链路跑通；自动识别与自动获取账单的方案尚未明确，不宜先猜。
- **风险**：如果一期就要求上传后自动出账，需要追加 OCR / 多模态识别模块 —— **此项已列入待确认问题**。
