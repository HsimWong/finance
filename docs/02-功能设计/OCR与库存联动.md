# OCR 识别与库存自动联动设计

> 2026-11-13 增量 2：把「截图自动识别后填入」和「家庭用品自动进入库存」提前到当前一期。

## 一、完整链路

```
上传账单截图
  ↓ 图片字节写 SQLite BLOB（screenshots.data）
本地 OCR 引擎提取文本行（含坐标、置信度）
  ↓
纯 Go 规则解析：金额 / 日期时间 / 收支方向 / 商户 / 商品明细 / 分类 / 标签 / 库存品类 / 保质期
  ↓
生成「识别草稿」→ 前端自动填入录入表单 + 列出可编辑的商品明细
  ↓ 用户复核（可改数量、金额、品类、保质期，可取消某行入库）
一次提交 = 一个数据库事务
  ├─ 写入 entries（收支流水，关联截图）
  └─ 写入 stock_items + stock_movements（家庭用品自动入库）
```

**关键取舍**：识别结果先填表、由人确认后再落库，而不是识别完直接生成流水。OCR 不可能 100% 准确，尤其金额；自动填入 + 低置信度字段标黄，比"识别错了一条脏数据"成本低得多。用户确认后仍是**一次提交、一个事务**，不会只写流水不写库存。

## 二、OCR 引擎

| 项 | 选择 |
| --- | --- |
| 引擎 | RapidOCR（onnxruntime），自带中英文检测/识别模型 |
| 运行方式 | 纯本地离线推理，无网络请求、无需密钥，截图不出本机 |
| 与后端集成 | `scripts/ocr.py` 作为 sidecar：stdin 收图片字节，stdout 输出一行 JSON（文本行 + 坐标 + 置信度）；Go 用 `exec.CommandContext` 调用，90 秒超时 |
| 依赖安装 | `python -m pip install rapidocr_onnxruntime`（一次即可） |
| 可替换性 | 后端 `OCRProvider` 只依赖「图片字节 → 文本行」契约，换成 Tesseract、云 OCR 或多模态模型只需替换 Provider，解析与业务代码不动 |
| 降级 | 引擎未安装时自检失败，页面显示黄色提示并开放「粘贴账单文字」解析入口；同一套解析规则保证功能仍可用 |

启动时 Go 会同步自检引擎并缓存状态，`GET /api/ocr/status` 对外暴露。可用 `-ocr-python` 指定 Python 解释器路径。

## 三、结构化解析规则（纯 Go，无第三方 NLP）

| 字段 | 规则 |
| --- | --- |
| 总金额 | 给每个数字候选打分：含「实付/合计/总计/应付」+0.65、带 ¥ +0.25、支付成功附近 +0.2、位置靠前 +0.05；日期时间行里的数字 −0.6；取最高分，同分取较大值 |
| 日期时间 | `YYYY-MM-DD` / `YYYY年M月D日` / `M月D日`（补当前年）+ `HH:MM`；未识别则默认今天 12:00 |
| 收支方向 | 统计「收款/入账/退款/+¥」与「付款/支付/实付/消费/-¥」关键词出现次数，默认支出 |
| 商户与分类 | 关键词规则表，**顺序即优先级**：汽车类（维修 → 保养 → 保险 → 加油 → 停车）排在「交通出行」之前，否则「加油」「停车」永远被当成打车；其后依次是 外卖 / 超市生鲜 / 药店 / 宠物 / 打车 / 居住缴费 / 电商 / 餐饮 |
| 同名分类消歧 | `findCategoryID` 优先命中**叶子分类**：`保险` 归到 `汽车›保险` 而不是一级 `保险`；一级分类只在没有同名叶子时才用 |
| 商品明细 | 逐行取最右侧数字为金额，尾部「数量+单位」拆出，其余为品名；排除含合计/实付/优惠/订单号/配送费等汇总行 |
| 库存品类 | 品名关键词匹配 6 类规则（见下），只保留命中的家庭用品行 |
| 保质期 | 按品类默认天数从账单日期推算，前端可改 |
| 置信度 | 每字段单独打分，< 0.6 在复核区标「请复核」；整体置信度为四项加权平均 |

## 四、库存品类规则

| key | 名称 | 默认保质期 | 典型关键词 |
| --- | --- | --- | --- |
| cat_food | 猫罐头 | 365 天 | 猫罐头、猫粮、猫砂、猫条、宠物 |
| medicine | 药品 | 365 天 | 布洛芬、别嘌醇、二甲双胍、头孢、蒙脱石、维生素、创可贴、口罩 + **剂型词兜底** |
| fruit_veg | 瓜果蔬菜 | 7 天 | 白菜、菠菜、苹果、香蕉、番茄、香菇 |
| meat_egg_milk | 肉蛋奶 | 14 天 | 鸡蛋、牛奶、酸奶、猪肉、牛肉、虾 |
| seasoning | 调料 | 365 天 | 酱油、陈醋、蚝油、料酒、花椒、淀粉 |
| grain_oil | 粮油 | 180 天 | 大米、面粉、挂面、食用油、花生油、杂粮 |

**顺序即优先级**：调料排在粮油前，否则「酱油 / 蚝油」会被粮油的单字「油」误匹配（该问题已在实测中发现并修正）。品类规则由 `GET /api/meta` 的 `stock_rules` 下发给前端，前后端不会出现两套清单。

**药品靠剂型词兜底**：具体药名不可能穷举（别嘌醇缓释胶囊、厄贝沙坦分散片、头孢克肟颗粒……），所以除常见药名外，再匹配剂型词——胶囊、缓释、肠溶、分散片、咀嚼片、泡腾片、含片、片剂、颗粒剂、冲剂、口服液、滴眼液、软膏、乳膏、凝胶、喷雾剂、栓剂、注射液、糖浆、丸剂、贴膏等。同时排除含剂型词但非药品的商品：咖啡胶囊、薯片、虾片、麦片、鱼丸、肉丸、奶片等。

**品类判定优先级**（`resolveStockCategory`）：

1. 请求显式给了有效 `category_key`（前端下拉框、OCR 草稿）→ **以 key 为准**，显示名从规则表反查；
2. 未给品类 → 按物品名匹配关键词（含上面的剂型词）；
3. 显式选「其他」→ 尊重选择，不再猜；
4. 都推断不出 → 落「其他」。

> 第 1 条是 v3 修复的根因：早期无论有没有选品类，都只拿物品名去匹配关键词来定显示名，于是「别嘌醇缓释胶囊」选了药品、名字里却没有「药」字，被写成 `category_name='其他'`（库里出现 `key=medicine / name=其他` 的自相矛盾记录）。现在显式选择优先，并由 migration v3 把历史脏数据按 key 反查纠正。

## 五、自动入库联动

- 创建流水时若请求带 `stock_items`，与流水写入在**同一事务**完成：每项生成一条 `stock_items`（`auto_created=1`、`entry_id` 指向流水）和一条 `kind=in` 的 `stock_movements`。
- 编辑流水时只重建 `auto_created=1` 的关联项，**用户手工维护的库存不会被覆盖**。
- 删除流水时先清掉其自动生成的库存项（出入库记录级联删除），再删流水。
- 请求不带 `stock_items`（普通手工记账）时完全不碰库存；带空数组表示明确清空关联项。

## 六、库存日常操作与通报

- 每日消耗：`consume`，可指定数量，减到 0 自动置 `used_up`。
- 损耗报废：`waste`，减到 0 自动置 `wasted`。
- 手工入库 / 补录、编辑名称数量金额保质期状态、删除，均在库存页完成。
- 保质期剩 ≤ 3 天标「临期」、已过标「过期」，库存页顶部聚合通报（页面内提示）。**微信推送提醒仍留二期**。

## 七、已知限制

- 规则解析针对「品名 + 数量 + 金额」这类清晰账单行；排版复杂、多列小票或手写体可能需要人工补录，粘贴文本解析可作为兜底。
- OCR 对倾斜、反光、低分辨率截图敏感；识别行数为 0 时会明确报错。
- 品类关键词表是白名单，药品靠剂型词兜底，仍可能有识别不到的物品；手工入库时直接选品类、或在「编辑」里改品类即可修正（编辑弹窗已带品类下拉）。后续可把关键词做成可配置数据。
- 首次调用 OCR 需加载模型，约数秒；之后同一进程内的调用明显更快。
