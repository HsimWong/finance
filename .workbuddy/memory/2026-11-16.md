## 沙箱运行时长的调研结论

- **没有「只能跑 3 天」这种硬期限。** 机制是「闲置休眠（约 10 分钟无访问）→ 超时回收 → 下次访问自动重建」，**链接不变**。
- 实测：网关 11-13 深夜部署，11-16 09:36 仍可访问（约 2.5 天），链接未变、未失效；探测时 uptime 从 1s 起跳，证明此前处于休眠而非常驻。
- 关键推论：**链接长期有效 ≠ 进程常驻**。冷启动有一两秒延迟；回收会清空沙箱磁盘，所以 `data/registry.json` 不可靠，各程序 60s 心跳上报是必需品而非优化。

## 10:57 用户问「平时怎么拉起服务」→ 顺手补上自愈

- 现状：服务在 **09:17 之后停了**（日志最后一条是 `09:17:32 固定入口心跳正常`），计划任务 `FamilyFinance` 处于 Ready、`LastRunTime` 还停在 11-14 00:17。**任务只在 AtLogOn 触发一次，中途挂掉不会自己回来**——这是设计缺口。
- 拉起过程踩到老坑：`Start-ScheduledTask` 后新隧道 `podcast-relying-algorithm-mineral` 注册成功但边缘一直 **530**（`--resolve` 指定边缘 IP 仍 530，排除本地 DNS），属于「分了域名但边缘不认」。再重启一次换到 `worthy-treat-prince-divine` 才 401 正常。**quick tunnel 新建后约有一半概率拿到这种死域名**，将来可考虑在 `start_tunnel` 里加「探测 530/000 就杀掉重开，最多 3 次」。
- 改进：给 `FamilyFinance` 加第二个触发器 —— `Once` + `RepetitionInterval=PT15M`（Duration 留空=无限），与 AtLogOn 并存。配合 `MultipleInstances=IgnoreNew` 与 `start.sh` 的幂等性正好形成守护：
  - 服务活着 → `start.sh` 走 `while svc_up` 驻留 → 任务 Running → 15 分钟后触发被 IgnoreNew 跳过；
  - 服务挂了 → bash 退出 → 任务 Ready → 下次触发（≤15 分钟）自动拉起。
- 注意 `Stop-ScheduledTask` **不会**杀掉已跑的子进程（实测 finance 4640 / cloudflared 仍存活成孤儿），彻底停止要用 `bash scripts/start.sh --stop`（按 pid 文件 + 端口反查）。
